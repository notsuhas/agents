# Product flow design

Establish the user goal, audience, platform, constraints and expected handoff.
Inspect the real product or supplied artifacts before proposing a redesign.
Use Upsy for permitted account/design references; public references can use the
host's browser. Do not imply that a browser screenshot permits copying assets.

Read enabled specialist guidance that fits the work: Emil's design engineering,
Apple design, SwiftUI, Expo, mobile-native, animation or accessibility skills.
Resolve actual available names; do not load disabled siblings from a source cache.

Describe the flow and information architecture before styling components.
Cover entry, success, empty, loading, error, permissions and recovery where relevant.
For meaningful alternatives, vary navigation or interaction structure rather than
only colors. Explain the tradeoff briefly; avoid manufacturing multiple options
for a small fix.

For an implementation request, use the project's actual navigation, state and supported APIs.
Use real selectors and explicit open state for sheets/dialogs. Preserve existing
user work. Create assets through the host's available image workflow when needed.

For an audit, inspect the existing product and return findings without editing it.
Verify the existing product or implemented handoff with the active browser/device workflow. Exercise
secondary screens, narrow layouts, long content and recovery paths. Compare the
rendered result to supplied artifacts; list missing screens or untested states.
Provide a manual walkthrough when the user needs to review the result.

This workflow produces local designs, code and artifacts. It does not promise
native Figma canvas writes, editable Slides, proprietary template runtimes or
ChatGPT Sites publication. Discover the exact required integration through Upsy
before choosing a native-only exception.
